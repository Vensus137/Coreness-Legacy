# Роутинг агента и тулзы

> Контракт AI-агента на сценариях: входная точка → сбор контекста → семантический роутинг → выполнение функций → цикл или финал → формирование ответа.

## Типы сценариев

Сценарии делятся на типы по роли и месту в конвейере:

| Тип | Назначение | Примеры |
|-----|------------|---------|
| **Системные** | Обработка события, загрузка, роутинг, выполнение, лимиты, ошибки. Не вызываются пользователем напрямую. | `system_chat_handler`, `system_loading`, `system_routing`, `system_execution`, `system_execution_tool`, `response_error` |
| **Функции (tools)** | Сценарии для completion-запросов: вызываются оркестратором по имени. Собирают контекст или выполняют действия. | Будущие: поиск, RAG, файлы, мессенджеры и т.д. Имена по контракту (например `tool_<name>` или как задано в storage). |
| **Response** | Финальные сценарии ответа пользователю. Вызываются, когда контекст собран; делают completion и формируют ответ. | `response_general`, `response_default`, общий финализатор `response_finalization` |
| **Функции-обёртки** | Вспомогательные сценарии не для completion: сбор контекста (prompt, messages, chunks), подготовка данных. Вызываются из системного конвейера, не из выбора модели. | `function_prompt`, `function_messages`, `function_context` (в `config/scenarios/functions/`) |

Других типов пока не предполагается. При добавлении новых сценариев относи их к одному из этих типов и клади в соответствующую папку/блок конфига.

## Конвейер этапов (пайплайн)

Последовательность при сообщении из чата:

1. **Хендлер** — `system_chat_handler`: проверка источника (чат), запуск цепочки.
2. **Загрузка и настройки** — `system_loading`, `system_get_settings` (индикатор «Обрабатываю...», загрузка storage в кэш).
3. **Сбор контекста** — сценарии-функции: prompt, messages, chunks и т.д. (`function_prompt`, `function_messages`, `function_context`).
4. **Роутинг** — `system_routing` → `system_routing_step` (completion с выбором action- и response-функций) или при достижении лимита шагов → `system_routing_step_response` (только response-функции).
5. **Выполнение** — `system_execution`: если есть `tool_calls` → `system_execution_tool` (цикл по вызовам, затем снова роутинг); если `response_calls` → `system_execution_response` (один response-сценарий); иначе → `response_default`.
6. **Финал ответа** — выбранный response-сценарий делает completion и вызывает `response_finalization` (замена сообщения загрузки + отправка ответа в чат).

Итого: **хендлер → загрузка/настройки → сбор контекста → роутинг → выполнение функций → роутинг → ... → лимит шагов или выбор response → выполнение response → финализация → ответ**.

## Входная точка

- Обработка начинается с **события** (например, сообщение пользователя).
- Проверяется, что событие пришло **из чата (UI)** — тогда запускается цепочка (см. конвейер выше).
- Детали источника и полей события — в [EVENT_GUIDE.md](../reference/EVENT_GUIDE.md).

## Тулзы как сценарии

- **Тулз** в контексте агента — это **сценарий**, вызываемый по имени (например, `tool_<name>` или имя из списка в storage).
- Отдельный плагин для роутинга не вводится: тулзы — сценарии, объединённые соглашением по именованию и по месту хранения параметров и результата в кэше.

## Кэш: параметры и результат тулза

Используется общий кэш сценариев (`_cache`). Для каждого вызова тулза:

- **Параметры** (аргументы вызова) всегда лежат в **`_cache.tools.<name>.arguments`**.
- **Результат** выполнения тулза кладётся **туда же** — в `_cache.tools.<name>` (например, в тот же объект добавляются поля с ответом шагов сценария или отдельный ключ `result` — по контракту конкретного тулза).

Пример: для тулза `tool_download_rag` перед запуском сценария в `_cache.tools.download_rag.arguments` передаётся объект с полями (url, опции и т.д.); после выполнения сценария результат доступен в `_cache.tools.download_rag` (и при необходимости в плейсхолдерах вида `{_cache.tools.download_rag...}`).

## Хранение настроек (storage)

Все настройки роутинга и списков функций хранятся в **системном storage**: `config/storage/system.yaml`, группа **`system`**.

- **Роутинг**: `routing_model`, `routing_prompt`, `routing_steps_limit`, `routing_messages`, `routing_messages_chars`, `routing_chunks`, `routing_chunks_chars`.
- **Списки функций для completion**: `routing_tools` (action-функции), `routing_response_tools` (только response-функции при финальном шаге или лимите).
- **Описания функций (схемы)** — в той же группе, под ключом **`tools`**: каждая функция задаётся полем с именем (например `response_general`, `response_default`) и схемой для LLM (`type: function`, `function.name`, `function.description`, `function.parameters`).

В сценариях после `get_storage` с `group_key: "system"` значения доступны в кэше (например `_cache.system.routing_model`, `_cache.system.routing_tools`).

**Масштабирование:** когда функций станет много, список схем можно вынести в отдельный файл storage (например `config/storage/tools.yaml`) и подключать его в систему; пока все настройки в одном файле, но в разных группах (`system` — общее, `tools` — схемы функций).

## Базовый поток (кратко)

1. Приходит **событие** (например, сообщение из чата).
2. **Хендлер** — проверка источника (чат), загрузка, настройки, сбор контекста (prompt, messages, chunks).
3. **Роутинг** — модель по контексту выбирает, какие функции выполнить (action и/или response).
4. **Выполнение** — аргументы в **`_cache.tools.<name>.arguments`**, запуск сценариев по имени; результаты в **`_cache.tools.<name>`**.
5. Цикл: снова роутинг, пока не выбран response-сценарий или не достигнут лимит шагов; затем один response → финализация → ответ в чат.

Подробная последовательность этапов — в разделе [Конвейер этапов](#конвейер-этапов-пайплайн) выше.

## Роль модели оркестрации

Модель **только оркестрирует**: на каждой итерации решает, что выполнить дальше (какие тулзы вызвать). Сама она не формулирует ответ пользователю и **не уточняет у пользователя** — уточнение, ответ и прочее делают тулзы (например, response-тулз с диалогом). Задача модели — выбор из списка тулзов по контексту; тулзов может быть очень много (поиск, сохранение в RAG, открытие/запись файлов, ответ и т.д.). За один шаг допускается вызов **нескольких тулзов** (вопрос синхронизации и параллелизма — отдельно).

## Response-тулзы (финал сбора контекста)

Когда контекст собран и выполнять больше ничего не нужно, модель должна выбрать **response-тулз** — сценарий, который сформирует ответ пользователю (и при необходимости уточнение). Чтобы модель это понимала, response-тулзы нужно явно оформлять:

- **Именование**: например префикс или суффикс в имени (`tool_response_*`, `*_response`) или отдельная метка в описании.
- **Описание в списке тулзов**: явно указывать, что тулз является «финалом» / response (например: «Ответ пользователю по собранному контексту; выбери, когда больше не нужно вызывать другие тулзы»).
- **Отдельный блок в контексте**: при формировании промпта для LLM можно передавать список тулзов двумя группами — «действия» (поиск, сохранение, …) и «response» (варианты ответа по контексту). Модель выбирает из «действий», пока нужно что-то делать, и переходит к выбору из «response», когда контекст готов.

Конкретный способ (поля в схеме тулза, разделение списков в промпте и т.д.) задаётся при реализации роутера.

## Развитие сценариев (масштабирование)

При добавлении новых возможностей агента:

1. **Определи тип сценария** — системный, tool, response или функция-обёртка (см. [Типы сценариев](#типы-сценариев)).
2. **Размещение файлов**:
   - Системные — `config/scenarios/system/` (при необходимости новые файлы, нумерация по порядку в пайплайне).
   - Response — `config/scenarios/responses/`; финализатор (общий шаг замены загрузки и отправки ответа) можно вынести в отдельный сценарий (например `99_finaliztion.yaml`).
   - Функции-обёртки (сбор контекста) — `config/scenarios/functions/`.
   - Tools (функции для вызова оркестратором) — пока можно в `config/scenarios/tools/` или рядом с responses; при росте — отдельная папка/структура.
3. **Регистрация в storage** — для каждой функции, которую должна вызывать модель, добавь схему в `config/storage/system.yaml` в блок `tools` и при необходимости добавь ссылку в `routing_tools` или `routing_response_tools` (плейсхолдер вида `{_cache.tools.<name>|fallback:}`).
4. **Response-функции** — имена с префиксом `response_` и явное описание в схеме («финальный ответ…»), чтобы модель отличала их от action-функций.
5. **Вынесение списка функций** — при большом количестве тулзов завести отдельный storage-файл (например `tools.yaml`) с группой `tools` и подгружать его вместе с `system.yaml`.

Системный пайплайн (хендлер → загрузка → контекст → роутинг → execution) менять не обязательно: новые сценарии подключаются через storage и вызов по имени из `system_execution_tool` / `system_execution_response`.

## Промпт и контекст вызова

- **Промпт оркестрации (роутинга)** хранится в **storage**, группа **`system`**, ключ **`routing_prompt`** (`config/storage/system.yaml`). В нём задаются правила выбора action- и response-функций. Универсальный системный промпт для всего агента при необходимости можно вынести в ключ **`agent_system`** той же группы.
- **Контекст вызова дополняется**: к промпту роутинга подставляются prompt пользователя, messages, chunks из кэша (`_cache.ai_agent.*`); список тулзов берётся из `routing_tools` или `routing_response_tools`. Для вложенных тулзов в контекст можно передавать описание текущей ситуации и список дочерних функций.
